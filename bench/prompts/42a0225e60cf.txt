INVARIANT 1: QE's nat (number of atoms) and ntyp (number of distinct elements) MUST be computed from the actual ASE Atoms object in hand -- e.g. len(atoms), len(set(atoms.get_chemical_symbols())) -- never hardcoded as a literal number typed from memory, a note, or an example script. Immediately after writing (or editing) any Quantum ESPRESSO input file, call validate_qe_input on it; treat a failed validation exactly like a run_python error under rule 3 -- fix the generating code (not the printed number) and rewrite the file.

INVARIANT 2: the number of valence electrons / occupied bands used anywhere in a DFT calculation is a property of the specific pseudopotential used, not the element -- semicore pseudopotentials (e.g. filenames containing 'spn') include extra core-like shells as valence and can roughly double the naive per-element count. NEVER assume or compute this from a 'typical' valence-electron count typed from memory (e.g. Ti has 4 valence electrons, O has 6). This matters in at least two places: (a) any post-processing script that aligns a band structure (VBM/CBM/Fermi-level shift) -- an assumed wrong occupied-band count silently produces a plot that looks plausible (axes, labels, a line) but is shifted/misaligned so the bands look wrong (e.g. spuriously crossing zero, looking metallic); and (b) 'nbnd' in a bands-calculation input file. Before an SCF run exists, estimate the electron count in code by summing z_valence over every atom -- the value get_pseudopotential reports as file.z_valence, which a script reads from the same file with `from chem_llm.tools.upf import read_upf_header; read_upf_header(path)['z_valence']` (do not write your own UPF parser). A pseudopotential's valence often includes semicore states, so it is usually MORE than the textbook valence. Pad nbnd above half of it; once an SCF pw.out exists, treat its 'number of electrons' line as ground truth and re-check nbnd against it (occupied bands = that value / 2 for a spin-unpolarized non-metallic run) -- 'number of Kohn-Sham states' in the same pw.out is that occupied-band count already computed for you. Never type a guessed number into a script; read/derive it from the actual pw.out in code. In a script, read pw.out ONLY through chem_llm.qe_output -- do not write your own regex for it (hand-written ones have repeatedly missed QE's actual line formats):

    pw = read_pw_out('calculations/000/pw.out')
    # pw['n_electrons'], pw['n_occupied'] (already 1 electron/band with spin-orbit),
    # pw['fermi_energy_eV'] (smearing runs), pw['spin_orbit'], pw['total_magnetization']
    edges = band_edges(E, pw['n_occupied'])   # -> edges['vbm'], edges['cbm'], edges['gap'] in eV

INVARIANT 3: the k-path of a bands calculation, the cell it runs on, and the band plot's x-axis all come from ONE k-path, produced by chem_llm.kpath (the same code as the get_kpath tool) for THIS structure -- never typed from memory, a textbook table, or another structure. In setup_jobs.py, for each structure:
    from chem_llm.kpath import standard_kpath, kp_atoms, kp_kpts, kp_save
    kp = standard_kpath(atoms)          # seekpath's standard path, evenly spaced
    prim = kp_atoms(kp)                 # THE cell for pw.in AND bands.in
    # bands.in: write_espresso_in(..., prim, ..., kpts=kp_kpts(kp))
    kp_save(kp, f'calculations/{nnn}/kpath.json')
Write prim -- not the CIF's cell -- into both inputs: the path's fractional k-points refer to prim's reciprocal basis, and a differently oriented cell silently puts them on the wrong k-points. Do not re-project, re-interpolate, re-label or re-order the k-points, and do not write a separate labels file: kpath.json holds the labels, tick positions (path discontinuities already joined as 'A|L') and the line segments. Recompute it per structure -- perturbed structures have lower symmetry and their own path. Call get_kpath on structure_000 first to see the path, and validate_qe_input on bands.in afterwards (it checks the k-points against kpath.json).

INVARIANT 4: the band plot's x-axis, ticks and line segments come from chem_llm.kpath.plot_axis(kpath.json, NNN.bands.dat), which also refuses to run if bands.x computed a different k-point list than kpath.json (so a plot can never silently mismatch the calculation). Use its x (path length) for the band curves, draw each of its segments as a separate line -- segments are slice objects: `for s in ax['segments']: plt.plot(x[s], E[s, band])`, never x[start:end+1] -- (no line across a discontinuity), put a vertical line and a tick label at every tick -- ax['tick_x'] and ax['tick_labels'] are plain lists for exactly that (ax['ticks'] holds the same as dicts with keys x/label/indices; do not unpack them as pairs) -- and never build ticks from k-point indices or typed labels. Choose the y-range deliberately: semicore bands sit tens of eV below the valence manifold, so after aligning to the VBM (or the Fermi energy for a metal) restrict the y-axis to about +/-10 eV unless the task asks otherwise.

INVARIANT 5: every physical quantity carries a UNIT, and the unit a tool reports is frequently not the unit the next file wants. Convert explicitly, in code, with the conversion written down -- never paste a number from one system into a field that means another. The specific trap in this pipeline: get_pseudopotential returns its recommended cutoff in HARTREE (the result's own `recommended_ecutwfc.unit` says so), while QE's ecutwfc/ecutrho are in RYDBERG. 1 Ha = 2 Ry, so writing the hint straight into ecutwfc silently runs the whole calculation at HALF the recommended cutoff -- nothing errors, the SCF still converges, and the resulting energies are quietly under-converged. Write `ecutwfc_ry = 2.0 * hint_ha` (and set ecutrho from the converted value, not the raw hint), and assert the number you wrote is the one you meant. The same care applies elsewhere: QE lengths are bohr unless the card says angstrom, ASE is angstrom throughout, bands.x writes energies in eV, and a .gnu k column is in 2*pi/alat.

INVARIANT 6: a Quantum ESPRESSO input variable must sit in the namelist the docs assign it to. Do NOT hand-sort variables into &CONTROL / &SYSTEM / &ELECTRONS yourself -- pass write_espresso_in a FLAT input_data dict and let ASE route each key to its correct namelist (ase.io.espresso.Namelist(...).to_nested(binary='pw') does the routing; e.g. it places conv_thr in electrons, ecutwfc and nat in system, calculation in control). RULE: magnetism

  ELSE (moment below 0.1 muB per formula unit) run nspin=1.
